# `presidio-hardened-vol-assign` v0.2.0 — Implementation Plan

Status: **in progress**. This plan supports the paper *"From Methodology to
Practice: A Production-Grade Decision Support Tool for Multi-Objective
Humanitarian Allocation in Resilient Supply Chains"* (Rabiei, Arias-Aranda &
Stantchev, in preparation).

v0.2.0 adds a **second optimisation model** — humanitarian allocation of
affected people to relief centres — **side by side** with the original 2023
ED-staffing model, which remains fully reproducible and unchanged in behaviour.

---

## 1. Guiding architecture: a domain-adapter layer

Today every layer is hard-wired to the 2023 ED-staffing problem. To run **both
models side by side**, we introduce a thin **domain adapter** abstraction and
refactor the existing code to sit behind it as the first adapter — *no
behavioural change to the 2023 model*.

New CLI selector:

```bash
pva assign --model ed-staffing   ...   # default → identical to v0.1.0
pva assign --model humanitarian  ...   # new 3-objective model
```

A `Domain` interface (new `domains/base.py`) exposes exactly the parts that
differ between the two problems:

| Hook | ed-staffing (existing) | humanitarian (new) |
|---|---|---|
| `load(...) -> ProblemInstance` | volunteers + EDs | people + centres |
| `objective_names` | `(z1, z2)` | `(z1, z2, z3)` |
| `reference_point` / `ideal_point` | `(1,1)` / `(0,0)` | `(1,1,1)` / `(0,0,0)` |
| genome init / crossover / mutation | permutation: `cxOrdered` + `mutShuffleIndexes` | integer: `cxUniform`/`cxTwoPoint` + `mutUniformInt` |
| `decode` + `evaluate` | greedy type-match -> 2 FIS means | person->centre map -> 3 FIS means |
| assignment-row schema | `fis1/2/3_score` | `fairness/transport/overcrowding` |

`solvers.py` becomes a **generic engine** (`engine.py`) parametrised by a
`Domain` — the NSGA-II / NRGA loop, `(mu + lambda)` survival, and Pareto
extraction are already domain-agnostic; only the operators and evaluator get
injected. This is the single most important refactor and the main risk surface
(see §6).

## 2. Input schema for the humanitarian model

**`people.csv`** — one row per affected person:

| Column | Type / range | Feeds | Meaning |
|---|---|---|---|
| `person_id` | string, unique | — | identifier (no PII, per Presidio rule) |
| `vulnerability` | float [0,10] | FIS-A | priority/need (elderly, injured, children) |
| `mobility` | float [0,10] | FIS-B | personal transport access (0 = immobile) |
| `group_size` | int [1,20], default 1 | FIS-C load | people moved together (load contribution) |
| `distance_center_<center_id>` | float [0,100] km | FIS-A, FIS-B | one column per centre (mirrors today's `distance_ed_*`) |

**`centers.csv`** — one row per relief centre:

| Column | Type / range | Feeds | Meaning |
|---|---|---|---|
| `center_id` | string, unique | — | identifier |
| `capacity` | int [1,5000] | FIS-C | nominal capacity (people) |
| `service_level` | float [0,10] | FIS-A | resource/quality level (staff, supplies) |
| `road_accessibility` | float [0,10] | FIS-B | route condition / access to the centre |

**Feasibility constraint (checked up front):** `Σ capacity ≥ Σ group_size`, and
each person assigned to exactly one centre — the analogue of today's "enough
volunteers" check in `validation.py`.

### The three new FIS (structure mirrors the existing 27-rule Mamdani systems)

| FIS | Output (minimise) | Inputs | Intuition |
|---|---|---|---|
| **FIS-A** Fairness in People Prioritization | `unfairness` [0,1] | `vulnerability` (person), `service_level` (centre), `distance` (pair) | high-vulnerability person sent far / to a low-service centre -> unfair |
| **FIS-B** Transportation Feasibility | `transport_infeasibility` [0,1] | `distance` (pair), `mobility` (person), `road_accessibility` (centre) | far + low mobility + poor route -> infeasible |
| **FIS-C** Center Allocation Balance | `overcrowding` [0,1] | `utilisation = Σ group_size assigned / capacity` (centre) | utilisation ≫ 1 -> overcrowded / imbalanced |

**Objectives:** `Z1 = mean(unfairness)`, `Z2 = mean(transport_infeasibility)`
over people; `Z3 = load-weighted mean(overcrowding)` over centres — all
minimised.

> Two items pending from the paper before the FIS internals are finalised:
> (1) the exact **membership functions and rule tables** (scaffolded now mirroring
> the existing trapezoid/triangle Low/Med/High structure; final numbers must
> match the paper's Tables 1–2 so code and manuscript agree); and (2) **FIS-C is
> structurally different** — its input (centre utilisation) is only known *after*
> a full allocation is decoded, so it cannot use the static per-pair cache the ED
> model relies on. It is precomputed as a 1-D utilisation->overcrowding lookup
> grid (101 points) so the evolutionary loop stays fast and deterministic.

## 3. Metrics: generalise from 2-D to N-D

`metrics.py` is currently hard-2-D (`hypot(z1,z2)`, sort-by-`z1` spacing, 2-D
sweep HV). Changes:

- **NNS** — unchanged.
- **MID** — `hypot` -> N-dim Euclidean norm to the ideal point. Backward-compatible in 2-D.
- **SM** — the "sort by z1, consecutive distance" definition does not generalise
  to 3-D. Switch to the standard **Schott nearest-neighbour spacing**
  (dimension-agnostic). This slightly changes the ED model's SM values; adopted
  as the correct, paper-defensible choice.
- **HV** — replace the bespoke 2-D sweep with **DEAP's built-in
  `tools.hypervolume`** (n-dimensional), reference `(1,…,1)`.
- **REP (new, reproducibility)** — the paper's "bit-for-bit" criterion: re-run a
  fixed seed twice, canonicalise the Pareto CSV, hash it (SHA-256), report
  `REP = 1.0` iff identical. Surfaced via `pva benchmark --check-repro`.

## 4. I/O, CLI, security, tests, docs

- **`writers.py`** — emit objective columns dynamically (`z1..zk`) from
  `objective_names`; `load_pareto_csv` auto-detects `z*` columns. Assignment CSV
  schema comes from the domain.
- **`cli.py`** — add `--model`; new `pva benchmark` (generates the paper's
  instances — small **5 centres / 150 people**, large **10 / 300** — runs both
  solvers, emits Table-3-style mean±std + REP) and `pva show` (figures, §5).
- **`validation.py`** — split into per-domain loaders; reuse all existing
  primitive validators (range / type / shell-injection guards) and the
  path-traversal guard unchanged.
- **`security.py`** — unchanged contract; startup log line also records `model=`.
- **Tests** — new humanitarian FIS, domain, 3-D metric, benchmark and repro
  tests, plus humanitarian fixtures; all existing ED tests stay green
  (regression guarantee for side-by-side). Hold ≥80% coverage.
- **Docs** — README humanitarian quick-start; roadmap rewritten (see §7).

## 5. Publication figures (`pva show`)

3-objective fronts -> **pairwise 2-D projections** (Z1–Z2, Z1–Z3, Z2–Z3) plus an
optional 3-D scatter, NSGA-II vs NRGA overlaid; static PNG/SVG export
(matplotlib) for the manuscript.

## 6. Risks / sequencing

Riskiest pieces, done first and behind tests:

1. **Engine refactor** (`solvers.py` -> generic `engine.py`) — land it with the
   ED domain *only* and prove the existing test suite passes before adding the
   new domain.
2. **3-D metrics** (esp. HV via DEAP, SM redefinition).
3. **Integer encoding + capacity** for the humanitarian decoder.

Phase order: (1) engine + domain refactor, ED-only, all green -> (2) N-D metrics
-> (3) humanitarian domain + FIS scaffold + fixtures -> (4) `benchmark` + REP ->
(5) `show` figures -> (6) docs/roadmap -> (7) release (PyPI publish + tag
`v0.2.0` + Zenodo DOI).

## 7. Version / roadmap reconciliation

The repo's *old* planned v0.2.0 (sensitivity + Pareto explorer) collides with
the paper's v0.2.0. Resolution: the humanitarian model **becomes v0.2.0**; the
sensitivity / explorer work **moves to v0.3.0**; benchmark reproducibility and
data connectors shift to v0.3.0+.

> Semver note: a 2->3 objective change plus a new domain is arguably a 1.0-level
> change, but the paper commits publicly to **v0.2.0**, so that is the shipped
> number.

## 8. Open confirm-points (non-blocking defaults)

1. FIS rule tables / MFs — scaffold now, drop in the paper's final Tables 1–2
   later. (default: yes)
2. SM redefinition to Schott nearest-neighbour (changes ED's SM slightly).
   (default: yes)
3. Capacity as a *soft* objective (folded into Z3) rather than a hard repair
   constraint. (default: soft — matches "minimise overcrowding" as an objective)
4. Schema field names / ranges above — open to renames or additions
   (e.g. `priority_need`, separate `route_condition`).
